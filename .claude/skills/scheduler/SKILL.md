# Scheduler

The **Scheduler** ([src/scheduler/scheduler.rs](../../../src/scheduler/scheduler.rs)) is the one service that creates job runs nobody asked for by hand. It is a **reconciler, not a clock**: each pass it looks at every schedule and submits a [`job_run`](../entities/references/job_run.md) for whichever of its next `submit_ahead` cron occurrences has none yet. **It only ever adds.** Nothing here deletes a run - not a surplus one, not one whose schedule has left the YAML - so a run the schedule has stopped asking for stays `Scheduled` and will be released and executed like any other.

**It never decides that a run is due.** A run it submits is due only once its `scheduled_at` arrives, and moving it from `Scheduled` to `Queued` at that moment is [`JobRunReleaser`](../orchestrator/SKILL.md)'s job alone — a different service, in the orchestrator, not this one. That split is why the two exist separately: the Scheduler answers "which runs, dated when, ought to exist for this schedule right now?", a question about cron math and the YAML; the releaser answers "has this run's moment come, or has somebody stopped it?", a question about the clock and one row at a time. Folding them together would make one service read both the schedule and the run to answer either question.

It is **not part of the [orchestrator](../orchestrator/SKILL.md)**, but it is driven by the same machinery: `Scheduler` is an `impl Service` ([src/poller.rs](../../../src/poller.rs)), started by a `Poller::new(...).start()` line in `ServeCmd::run` ([src/cli/commands/serve.rs](../../../src/cli/commands/serve.rs)) just like an orchestrator service. Its relationship to `Signals` ([src/signals.rs](../../../src/signals.rs)) is one-directional: it *publishes*, since submitting a job inserts a `job_run` row `JobRunReleaser` and (once released) `JobRunDispatcher` select on, but it does not *subscribe* — its `Poller` is given a standalone `Arc<Notify>` that nothing ever publishes to, rather than one registered on the shared bus, so it only ever wakes from its own one-second interval. That is deliberate, not an oversight: the reconcile changes with the clock, never with a status write, so registering it on the bus would wake it on every unrelated status change in the system for nothing.

`ServeCmd::run` starts the scheduler and the orchestrator side by side, and they share no state: the scheduler's entire output is a `CRUD::submit_job` call against `job_run` rows it does not otherwise touch, and everything from `Scheduled` onward — releasing, dispatching, executing, retrying, finishing — is the orchestrator's business (`JobRunReleaser` included). Keep it that way: the scheduler must never read a task run, and the only job run status it ever asks about is `Scheduled`.

That is why submitting a job here is **unconditional**, even one whose earlier occurrence is still running: `max_parallel_runs` is enforced in `JobRunDispatcher::settle_as_queued` and nowhere else, so an over-limit run submits like any other and queues there once released, instead of being dropped here. A concurrency check in this loop would have to count job runs by status, which is exactly the coupling the paragraph above rules out.

## Definition (YAML → in-memory `mem.schedule` + `mem.schedule_job`)

A schedule is a YAML file under `<data_dir>/schedules/*.yml`, parsed by `ScheduleYaml` ([src/yaml_models/schedule_yaml.rs](../../../src/yaml_models/schedule_yaml.rs)):

```yaml
id: nightly
name: Nightly
cron: "0 0 3 * * *"     # 6 fields, seconds first
timezone: Europe/Vienna # defaults to [schedule_defaults] in config.toml, itself UTC
start_date: 2026-01-01  # optional
end_date: 2026-12-31    # optional
disabled: false
submit_ahead: 1         # occurrences to keep submitted ahead of time; refused at 0
jobs:
  - id: my-job
```

`CRUD::init` ([src/crud/crud.rs](../../../src/crud/crud.rs)) inserts one `mem.schedule` row plus one `mem.schedule_job` row per listed job. Both tables are in-memory config data — see [schedule](../entities/references/schedule.md) and [schedule_job](../entities/references/schedule_job.md) in the entities skill.

## The reconcile

`Scheduler::select` (called by its `Poller` once a second) fetches **every** schedule — enabled or not, bounded or not — ordered by `row_id`, and `handle` reconciles each one:

1. **`CronTrigger::get_next_runs`** gives the next `submit_ahead` cron occurrences strictly after now — empty for a disabled schedule or one past its `end_date`, both falling out of the trigger's own bounds rather than needing a branch in the reconcile.
2. **`schedule_jobs`** is read once per pass, so "which jobs does this schedule name?" is one answer for every occurrence of that pass.
3. **`submit_if_missing`** runs per occurrence and per job the schedule names: it selects a job run on `schedule_id`, `job_id` and `scheduled_at` together, and submits only if none comes back — via `CRUD::submit_job`, exactly as `job submit` does, with that occurrence as `scheduled_at` and the schedule's own id as `schedule_id`. **A submit that fails is logged and stepped over**, so that one job loses that occurrence rather than jamming every other job or occurrence in the same pass — the next pass tries it again anyway.

**The existence check reads every status but `Deleted`, not only `Scheduled`.** It asks *"has this occurrence been dealt with?"*, and any run carrying this `schedule_id` and `job_id` at this instant says yes, whatever became of it. Reading only `Scheduled` would answer it wrongly in the one case the design itself creates: stopping a future-dated scheduled run is allowed (`src/shared/job_run.rs` gates only on `is_finished()`), `JobRunReleaser` then **skips it outright** rather than making the stop wait for the run's time — and the row leaves `Scheduled` while its instant is still in the future. The next pass would find the occurrence missing, submit a brand-new run for the identical instant, and the job the user cancelled would run anyway, leaving one more `skipped` row per attempt. Cancelling a single occurrence would be impossible.

**`Deleted` is the one status that frees an occurrence**, and the only way to get one back under an edited definition. `flowlite job-run delete <id>` tombstones a still-`Scheduled` run through `CRUD::delete_job_run` rather than erasing it, and the next pass sees the occurrence as unclaimed and submits it again from the job as the running server read it. So the two removals mean opposite things to this check: `Skipped` holds the instant for ever (the user cancelled it), `Deleted` releases it (the user wants it written again). Anything added to `JobRunStatus` therefore has to decide which side it falls on — `occupying_statuses()` in `scheduler.rs` is where that is spelled out.

**The instant is matched in SQL, as stored**, rather than compared in Rust: the row was inserted with the very value `get_next_runs` hands out here — a cron occurrence, whole seconds and UTC — so both sides encode identically. A caller passing an instant from anywhere else cannot rely on that.

**Running it again with nothing changed submits nothing new**, and nothing about a pass is written down: there is no cursor and no "what changed since last time?", because every pass re-derives its occurrences from the cron and the clock and asks the `job_run` table what already exists. What it does *not* do is undo anything — a lowered `submit_ahead`, an edited cron, a job dropped from `jobs:`, a disabled schedule or a deleted YAML file all leave their already-submitted future runs in place, and those runs will be released and executed.

## Gotchas

- **The cron fields are read in the schedule's own zone, so a DST change moves the UTC instant, not the local time.** `0 30 3 * * *` in `Europe/Vienna` is 02:30Z in winter and 01:30Z in summer. The two edges follow from that and are pinned by tests in [src/cron_trigger.rs](../../../src/cron_trigger.rs): an hour the spring change **skips** loses that day's run outright rather than moving it, so an 02:30 daily schedule fires 364 times in 2026; an hour the autumn change **repeats** fires on the first of the two, not both. Choose an hour outside 02:00-03:00 for anything that must run every day.
- **`cron` takes six fields, seconds first** (the `cron` crate's dialect), so a five-field expression copied from crontab silently means something else.
- **`schedule_job.parameters` reaches the command.** `submit_if_missing` passes it straight to `CRUD::submit_job` as that call's overrides, which checks it against the job's declared `parameters` and raises if a name here isn't one of them — so a typo in a schedule's `parameters` fails that job on every occurrence, the same "logged and skipped" way any other submit failure does.
- **A schedule naming a job that doesn't exist stops the server from starting.** `mem.schedule_job.job_id` is a foreign key to `mem.job`, and sqlx's `SqliteConnectOptions` turns `PRAGMA foreign_keys` on by default, so it is enforced. `CRUD::init` inserts every job before any `schedule_job`, so the bad reference aborts the whole config transaction with `(code: 787) FOREIGN KEY constraint failed` and the process exits before the scheduler ever ticks — one typo in one schedule file takes down `serve`, `job list` and `job submit` alike. So the reconcile never sees an unresolvable job id, and nothing here needs to handle one. (`job_run.job_id` itself has no foreign key — it can't, the job lives in the attached in-memory database — but `submit_job` selects the job before inserting anything and bails with `Job '<id>' not found`, so no run is ever created for a job that isn't there.)
- **An occurrence already submitted is recognised by an exact match on `scheduled_at`.** A cron occurrence has no sub-second part and is stored as it was bound, so this holds — but it is an equality across a SQLite round trip, and if it ever stopped holding the failure would be a duplicate run submitted every pass, visible only to somebody reading the table.
- **A run carries the YAML as it stood when it was *submitted*, not as it stands when it runs.** `CRUD::submit_job` snapshots the job's tasks, commands, env and parameters onto the run's own rows at submission time, and the reconcile submits up to `submit_ahead` occurrences in advance — so for `cron: "0 0 3 * * *"` with the default `submit_ahead: 1`, tonight's run was written just after 03:00 **yesterday**, and a job edited at 10:00 this morning does not affect it. This is a real change from firing at the moment the cron came due, where a run always carried the config of moments before. **And a running server never re-reads the edit at all.** `ServeCmd::run` calls `CRUD::init` exactly once, at startup, to seed `mem`; there is no watcher and nothing anywhere reloads it, so every occurrence that server submits — for the rest of its life — carries the YAML as it stood at that startup, not as it stands on disk now. An edit takes effect only for occurrences submitted after it: nothing here rewrites a run already submitted, so an occurrence written under the old YAML runs under the old YAML. The lever is `flowlite job-run delete <id>`, which tombstones a still-`Scheduled` run as `Deleted` — the one status the existence check ignores — so the next pass writes that occurrence again from the YAML the restarted server read. Stopping it instead settles it `Skipped`, which holds the instant for ever. Nothing else removes a run; only retention ever deletes rows. The same is true of a schedule's own per-job `parameters:` — the existence check keys a run on `(schedule_id, job_id, scheduled_at)` and does not compare parameters, so an edited override reaches only runs submitted by a server that has read the new file.
- **Nothing about a pass is written down.** The schedule row carries no cursor and no next-run column: every pass re-derives its occurrences from the cron and the clock, so there is no catch-up for occurrences whose time passed while the process was down — they are simply not among the next `submit_ahead` occurrences after the moment it comes back. The `job_run` rows are the history — see [job_run.md](../entities/references/job_run.md). The dashboard's "next run" is derived per request the same way, with `CronTrigger::get_next_run(None)`.
