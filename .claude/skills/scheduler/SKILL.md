# Scheduler

The **Scheduler** ([src/scheduler/scheduler.rs](../../../src/scheduler/scheduler.rs)) is the one service that creates job runs nobody asked for by hand. It is a **reconciler, not a clock**: each pass it looks at every schedule and makes that schedule's outstanding `Submitted` [`job_run`](../entities/references/job_run.md) rows equal its next `submit_ahead` cron occurrences — submitting whatever is missing, deleting whatever is surplus — and separately sweeps up the runs of any schedule that has left the YAML entirely.

**It never decides that a run is due.** A run it submits is due only once its `scheduled_at` arrives, and moving it from `Submitted` to `Queued` at that moment is [`JobRunReleaser`](../orchestrator/SKILL.md)'s job alone — a different service, in the orchestrator, not this one. That split is why the two exist separately: the Scheduler answers "which runs, dated when, ought to exist for this schedule right now?", a question about cron math and the YAML; the releaser answers "has this run's moment come, or has somebody stopped it?", a question about the clock and one row at a time. Folding them together would make one service read both the schedule and the run to answer either question.

It is **not part of the [orchestrator](../orchestrator/SKILL.md)**, but it is driven by the same machinery: `Scheduler` is an `impl Service` ([src/poller.rs](../../../src/poller.rs)), started by a `Poller::new(...).start()` line in `ServeCmd::run` ([src/cli/commands/serve.rs](../../../src/cli/commands/serve.rs)) just like an orchestrator service. Its relationship to `Signals` ([src/signals.rs](../../../src/signals.rs)) is one-directional: it *publishes*, since submitting a job inserts a `job_run` row `JobRunReleaser` and (once released) `JobRunDispatcher` select on, but it does not *subscribe* — its `Poller` is given a standalone `Arc<Notify>` that nothing ever publishes to, rather than one registered on the shared bus, so it only ever wakes from its own one-second interval. That is deliberate, not an oversight: the reconcile changes with the clock, never with a status write, so registering it on the bus would wake it on every unrelated status change in the system for nothing.

`ServeCmd::run` starts the scheduler and the orchestrator side by side, and they share no state: the scheduler's entire output is a `CRUD::submit_job` or `CRUD::delete_job_runs_with_children` call against `job_run` rows it does not otherwise touch, and everything from `Submitted` onward — releasing, dispatching, executing, retrying, finishing — is the orchestrator's business (`JobRunReleaser` included). Keep it that way: the scheduler must never read a task run, and the only job run status it ever asks about is `Submitted`.

That is why submitting a job here is **unconditional**, even one whose earlier occurrence is still running: `max_parallel_runs` is enforced in `JobRunDispatcher::settle_as_queued` and nowhere else, so an over-limit run submits like any other and queues there once released, instead of being dropped here. A concurrency check in this loop would have to count job runs by status, which is exactly the coupling the paragraph above rules out.

## Definition (YAML → in-memory `mem.schedule` + `mem.schedule_job`)

A schedule is a YAML file under `<data_dir>/schedules/*.yml`, parsed by `ScheduleYaml` ([src/yaml_models/schedule_yaml.rs](../../../src/yaml_models/schedule_yaml.rs)):

```yaml
id: nightly
name: Nightly
cron: "0 0 3 * * *"     # 6 fields, seconds first
timezone: Europe/Vienna # defaults to [schedule_defaults] in config.toml, itself UTC
start_date: 2026-01-01  # optional
end_date: 2026-12-31    # optional
disabled: false
submit_ahead: 1         # occurrences to keep submitted ahead of time; refused at 0
jobs:
  - id: my-job
```

`CRUD::init` ([src/crud/crud.rs](../../../src/crud/crud.rs)) inserts one `mem.schedule` row plus one `mem.schedule_job` row per listed job, and writes a first `next_run` right there with `CronTrigger::get_next_run(None)` — purely so the dashboard has something to show before the scheduler's first pass runs. Both tables are in-memory config data — see [schedule](../entities/references/schedule.md) and [schedule_job](../entities/references/schedule_job.md) in the entities skill.

## The reconcile

`Scheduler::select` (called by its `Poller` once a second) fetches **every** schedule — enabled or not, whatever its `next_run` — ordered by `row_id`, then sweeps orphaned runs (below) before `handle` reconciles each one:

1. **`desired_occurrences`** computes the next `submit_ahead` cron occurrences strictly after now — empty for a disabled schedule or one past its `end_date`, both falling out of the same `CronTrigger::get_next_run` call rather than needing a branch of their own.
2. **`outstanding_runs`** selects this schedule's own `Submitted` job runs — the ones nobody has released or taken back yet. **`runs_of_schedule`** selects this schedule's runs across *every* status, which is what the submit side compares against; the two sides of one reconcile deliberately read different sets, for the reason under "Two sets, not one" below.
3. **`delete_surplus_runs`** deletes whichever outstanding runs the schedule no longer asks for, through `CRUD::delete_job_runs_with_children`. **Surplus is keyed on the job and the instant together**, the same pair the submit side writes on: a run survives only if the schedule still names its `job_id` *and* its `scheduled_at` is still a desired occurrence. Keyed on the instant alone, a job removed from a schedule's `jobs:` list would keep its already-submitted future run and go on to execute it, because some other job of the schedule still wants that occurrence. Only future-dated ones: a run whose instant has already arrived belongs to `JobRunReleaser` from that moment on, and deleting it here would cancel a run at the exact moment it came due — the delete's own filter re-asserts `status = Submitted` and `scheduled_at > now` inside its transaction, so a row the releaser promoted between the select and the delete is left alone. Deleted rather than stopped: a run cancelled before it was ever due never happened, and a `job_run_stop` row would put it in the history beside runs that were genuinely stood down — this reconcile also recreates whatever it wrongly removes on the next pass, which a stop row would not.
4. **`submit_missing_runs`** submits, per occurrence and per job the schedule names, whichever combination has no run at all yet — via `CRUD::submit_job`, exactly as `job submit` does, with that occurrence as `scheduled_at` and the schedule's own id as `schedule_id`. **A submit that fails is logged and skipped with `continue`**, so that one job loses that occurrence rather than jamming every other job or occurrence in the same pass — the next pass tries it again anyway.
5. **`next_run` is written last, from `desired.first()`** — the earliest occurrence this pass computed, or `NULL` if there was none. This is a display value only, produced fresh every pass; nothing in the reconcile reads it back.

### Two sets, not one

**The submit side reads every status; the delete side reads only `Submitted`.** They are not the same question and must not share an answer.

The submit side asks *"has this occurrence been dealt with?"*, and any run carrying this `schedule_id` at this instant says yes, whatever became of it. Reading only `Submitted` there would answer it wrongly in the one case the design itself creates: stopping a future-dated scheduled run is allowed (`src/shared/job_run.rs` gates only on `is_finished()`), `JobRunReleaser` then **skips it outright** rather than making the stop wait for the run's time — and the row leaves `Submitted` while its instant is still in the future. The next pass would find the occurrence missing, submit a brand-new run for the identical instant, and the job the user cancelled would run anyway, leaving one more `skipped` row per attempt. Cancelling a single occurrence would be impossible.

The delete side asks *"may I take this run back?"*, and only a run nobody has acted on may be taken back — so it stays on `Submitted`, with the status re-asserted on the delete's own filter.

**This is convergent, not additive: running it again with nothing changed submits nothing new.** Every case the design has to handle — a first pass, a top-up after `JobRunReleaser` takes an occurrence, a restart, `submit_ahead` moving either way, an edited cron, a schedule being disabled — is the same two loops (delete-what's-surplus, submit-what's-missing) finding a different difference between "what's outstanding" and "what's desired". There is no "what changed since last time?" to get wrong, because nothing about the previous pass is remembered between passes — everything is re-derived from the schedule row and the `job_run` table as they stand right now.

**Orphaned runs are swept separately, at the head of `select`, not inside the per-schedule reconcile.** `delete_orphaned_runs` looks at every schedule-owned `Submitted` run still in the future and deletes any whose `schedule_id` no longer names a schedule in the set `select` just fetched — the case a YAML file being deleted leaves behind, since `delete_surplus_runs` only ever touches the schedule it is reconciling and a deleted schedule reconciles nothing. It runs once per pass on the whole set rather than per schedule, because `Service::Row` is `Schedule` and `handle` is never called for a schedule that no longer has a row. A run with no `schedule_id` — a manual submission — is never touched by either sweep. **Its errors are logged and swallowed, not propagated**, even though it runs inside `select`: `Poller::run` kills its loop on a `select` error and waits out `error_backoff`, so one undeletable row — an `SQLITE_BUSY` from a concurrent retention transaction, say — would cost every schedule its reconcile, and would do so again on every pass, stalling the Scheduler indefinitely. One orphan left standing for a pass is the smaller failure, and the next pass retries it. Same treatment `submit_missing_runs` gives an unsubmittable job, for the same reason.

## Gotchas

- **The cron fields are read in the schedule's own zone, so a DST change moves the UTC instant, not the local time.** `0 30 3 * * *` in `Europe/Vienna` is 02:30Z in winter and 01:30Z in summer. The two edges follow from that and are pinned by tests in [src/cron_trigger.rs](../../../src/cron_trigger.rs): an hour the spring change **skips** loses that day's run outright rather than moving it, so an 02:30 daily schedule fires 364 times in 2026; an hour the autumn change **repeats** fires on the first of the two, not both. Choose an hour outside 02:00-03:00 for anything that must run every day.
- **`cron` takes six fields, seconds first** (the `cron` crate's dialect), so a five-field expression copied from crontab silently means something else.
- **`schedule_job.parameters` reaches the command.** `submit_missing_runs` passes it straight to `CRUD::submit_job` as that call's overrides, which checks it against the job's declared `parameters` and raises if a name here isn't one of them — so a typo in a schedule's `parameters` fails that job on every occurrence, the same "logged and skipped" way any other submit failure does.
- **A schedule naming a job that doesn't exist stops the server from starting.** `mem.schedule_job.job_id` is a foreign key to `mem.job`, and sqlx's `SqliteConnectOptions` turns `PRAGMA foreign_keys` on by default, so it is enforced. `CRUD::init` inserts every job before any `schedule_job`, so the bad reference aborts the whole config transaction with `(code: 787) FOREIGN KEY constraint failed` and the process exits before the scheduler ever ticks — one typo in one schedule file takes down `serve`, `job list` and `job submit` alike. So the reconcile never sees an unresolvable job id, and nothing here needs to handle one. (`job_run.job_id` itself has no foreign key — it can't, the job lives in the attached in-memory database — but `submit_job` selects the job before inserting anything and bails with `Job '<id>' not found`, so no run is ever created for a job that isn't there.)
- **Comparing occurrences is done at whole seconds**, through `is_same_instant`. A cron occurrence has no sub-second part, but an instant that has round-tripped through SQLite has been through a string, and an equality that depended on that round trip being exact would fail by deleting and resubmitting the same run every pass — the most expensive way this could go wrong and the least visible.
- **A run carries the YAML as it stood when it was *submitted*, not as it stands when it runs.** `CRUD::submit_job` snapshots the job's tasks, commands, env and parameters onto the run's own rows at submission time, and the reconcile submits up to `submit_ahead` occurrences in advance — so for `cron: "0 0 3 * * *"` with the default `submit_ahead: 1`, tonight's run was written just after 03:00 **yesterday**, and a job edited at 10:00 this morning does not affect it. This is a real change from firing at the moment the cron came due, where a run always carried the config of moments before. **And a running server never re-reads the edit at all.** `ServeCmd::run` calls `CRUD::init` exactly once, at startup, to seed `mem`; there is no watcher and nothing anywhere reloads it, so every occurrence that server submits — for the rest of its life — carries the YAML as it stood at that startup, not as it stands on disk now. An edit takes effect only once the server has been restarted, and even then only for the runs whose occurrence changes as a result: the reconcile replaces an outstanding run whose occurrence the schedule no longer wants, but a run whose occurrence is unchanged keeps the definition it was already submitted with. There is also no user-facing way to delete a job run at all — no CLI subcommand, no MCP tool, no dashboard route; only the reconcile and retention ever delete one — so a restart is the only lever a user has. The same is true of a schedule's own per-job `parameters:` — the reconcile keys a run on `(job_id, scheduled_at)` and does not compare parameters, so an edited override reaches only runs submitted by a server that has read the new file.
- **`next_run` is not, and no longer was ever meant to be, a record of anything.** It is recomputed from scratch on every pass and every restart; there is no catch-up for occurrences whose time passed while the process was down, they are simply not among the next `submit_ahead` occurrences after the moment the process comes back. The `job_run` rows are the history — see [job_run.md](../entities/references/job_run.md).
